# Управление бюджетом, API 0.11.0

## Состояние и совместимость

`LocalBudget.balance` остаётся единственным денежным остатком. Основная работа, бизнес, обязательства и активы используют существующий `AdultState`. Новое необязательное `AdultState.budgetManagement` хранит часы основной работы, подработку и её историю, условия бизнеса, стратегию накоплений и историю продаж. Второго кошелька нет.

Кнопки и сюжетные решения используют общие `CareerSystem`, `AdultEconomy` и `AssetSales`. Будущая выплата определяется текущей `career`; сюжеты прежнего работодателя проверяют ID занятости. Открытие дела из каталога создаёт обычную предпринимательскую цепочку с последующей проверкой результатов. Успешные команды также записываются в летопись и систему важных решений.

Миграция **V10** добавляет nullable `life_session_action.budget_result` для сохранения исхода команды, включая отказ при найме или повышении. Старые JSON не переписываются: отсутствующие поля означают прежнее поведение. Прежние `/finances`, `/spending`, `/purchases`, `/step`, `/advance` и `simulation.adult` остаются доступны.

Новые GET поддерживают сгенерированные `local`. В детстве можно читать доходы и расходы; новые изменяющие команды доступны с 18 лет. Для старого демонстрационного `local` без `simulation` и для `1in8b` обёртка возвращает `available=false`, объяснение и `data/currency/periodMonths=null`; POST возвращает `409 BUDGET_UNSUPPORTED`. Внешний API при чтении и командах бюджета не вызывается.

## Маршруты

Все пути ниже относительно `/api/v1/sessions/{sessionId}`. Гостевая cookie `life_owner` обязательна; чужая сессия возвращает 404.

| Метод и путь | Данные |
| --- | --- |
| GET `/budget/income` | Доходы за 12 месяцев, источники, основная работа, подработка, бизнес, накопления |
| GET `/budget/expenses` | Расходы за 12 месяцев, категории, обязательства и прогноз на два месяца |
| GET `/budget/jobs` | Шесть основных вакансий, основания повышения, текущая работа и возможность увольнения |
| GET `/budget/side-jobs` | Три подработки, текущая дополнительная занятость и возможность увольнения |
| GET `/budget/businesses` | Три варианта бизнеса и текущий результат |
| GET `/budget/strategies` | Семь стратегий, их доступность и сохранённый выбор |
| GET `/budget/assets` | Активы с устойчивыми ID и история продаж |
| GET `/budget/assets/{assetId}/sale-preview` | Цена, залог, чистое поступление, прекращаемое содержание и прогноз |
| POST `/budget/actions` | Изменяющая команда; полный актуальный Session с `budgetAction` |

Все GET имеют обёртку:

```json
{
  "version": 12,
  "currency": "RUB",
  "periodMonths": 12,
  "available": true,
  "reason": null,
  "data": {}
}
```

Тип `data` зависит от маршрута и описан в [openapi.yaml](openapi.yaml). GET ничего не сохраняет и не продвигает время. Доступность конкретного действия находится у варианта в `data`, даже если весь раздел доступен для чтения.

## Единицы и бухгалтерия

Все суммы этих маршрутов — основные единицы **игровых RUB**, с точностью до копейки. Внутри `LocalBudget` хранятся целые копейки. Это не пересчёт статистических USD/PPP_USD в рубли. Вложенные ставки работы имеют `periodMonths=1`; годовое содержание явно называется `yearlyUpkeepStopped`.

Фактические итоги охватывают `(текущий месяц − 12; текущий месяц]`. `monthlyAverage` делится на **12**, даже если персонаж только начал работать. Это среднее за выбранное окно, не среднее за месяцы занятости. Округление до копеек HALF_UP.

- Сумма `income.sources.amount` равна `income.total` и `/finances.summary.income`.
- Сумма `expenses.categories.amount` равна `expenses.total` и `/finances.summary.expenses`.
- `FINANCING` исключён из этих итогов: получение займа, возврат/перемещение капитала, продажа обычного имущества, погашение основного долга.
- Проценты по долгу, обычные покупки, содержание, вложения в открытие дела, расходы бизнеса, реализованный инвестиционный убыток относятся к `OPERATING`.
- При реализации инвестиционного актива прибыль/убыток выделяются отдельно от капитала. Убыток сопровождается компенсирующей записью `FINANCING`, чтобы денежный остаток изменился ровно на цену продажи.

В `/finances.ledger` добавлены `sourceId`, `categoryId`, `relatedId`. Машинные ключи не извлекаются из русских названий. Категории: `HOUSING`, `FOOD_SHOPPING`, `PROPERTY`, `CHILDREN_EDUCATION`, `PETS`, `HEALTH`, `LEISURE_GIFTS`, `OTHER`.

Для новых операций известны, например, источники `SALARY`, `SECONDARY_SALARY`, `BUSINESS_REVENUE`, `BUSINESS_COST`, `BUSINESS_START`, `PARTNER_CONTRIBUTION`, `PENSION`, `SAVINGS_RETURN`, `PURCHASE`, `ASSET_UPKEEP`, `DEBT_INTEREST`, `DEBT_PRINCIPAL`, `ASSET_SALE`, `CAPITAL_RETURN`, `INVESTMENT_PROFIT`, `INVESTMENT_LOSS`. Старые ID позволяют однозначно распознать некоторые источники, покупки связываются по UUID. Старые объединённые расходы остаются в `OTHER` (`LEGACY_MIXED_LIVING`); неизвестные поступления — `LEGACY_UNCLASSIFIED` или `LEGACY_EARNINGS`. Они входят в итоги, но им не придумывается детализация.

Будущие прежние объединённые расходы на жизнь разделяются по явному **игровому допущению**: 40% жильё, остаток питание и повседневные покупки. Общая сумма не меняется. Это не национальная статистика потребления. Категория `OTHER` также включает затраты бизнеса и проценты; потребительскую разбивку нельзя дополнительно складывать с основным долгом.

## Работа и подработка

`primary.basePay` — договорная месячная оплата, `expectedPay` — прогноз с текущей работоспособностью, `workCapacityPercent` — ограничение активными болезнями. `actualIncome` — реально проведённые выплаты по ID этой занятости за последние `actualPeriodMonths=12`. Сводные `sources` включают также прошлых работодателей в окне. Для старой зарплаты без надёжной связи с занятостью `actualIncome=null`; это не ноль. Для `BUSINESS` использовать отдельный блок `business`, а не зарплату.

`currentTenureMonths` считается от начала текущей работы; `totalExperienceMonths` сохраняет общий опыт основной занятости. Подработка имеет собственный опыт. Неизвестные часы старой работы возвращаются `null`; в таком случае сервер блокирует совмещение, пока нагрузка не станет известной после смены работы. Зарплаты предложений используют существующую калибровку страны, если она записана в сохранении; абсолютные RUB и условия вакансий остаются игровыми.

Вакансии `warehouse`, `cook-assistant`, `support`, `repair`, `analyst`, `part-time-office` включают фильтры `noExperience` и `experienceMatch`. `available` дополнительно учитывает образование, квалификацию, здоровье, возраст, учёбу и суммарные часы. Для аналитика нужен завершённый HIGHER; очная учёба совместима с работой до 24 часов. Наём доступен с 18 лет до игровой пенсии в 65, при здоровье от 30. Итог основной заявки вероятностный. Совпадение seed, месяца, вакансии и текущих условий даёт тот же исход при разных ключах; сетевой повтор того же ключа использует записанный результат. Успешный каталоговый наём сразу EMPLOYED; сюжетный найм сохраняет испытательный срок.

Повышение: `results` (+15%, удовлетворённость работой от 60), `tenure` (+10%, год на текущем месте), `responsibility` (+20%, ещё 4 часа в неделю). Нужна постоянная работа и не менее шести месяцев на месте; между одобренными повышениями — минимум шесть месяцев. Это предварительные условия, `guaranteed=false`. Вероятность одобрения зависит от результатов/старательности; отказ не меняет параметры жизни. Новый запрос не следует отправлять автоматически после отказа.

Подработки: `weekend-help` (8 часов), `evening-support` (12), `tutoring` (8, требуется высшее образование). Совокупная нагрузка не более 60 часов в неделю. Если она больше 48, при пересечении каждого полного игрового года здоровье и счастье уменьшаются на 2. Подработка оплачивается за каждый следующий прожитый месяц с учётом работоспособности. При найме, чтении, ответе на решение или восстановлении деньги за будущие месяцы не начисляются.

Увольнение основной работы завершает её историю и будущую зарплату, сохраняя подработку и прочие доходы. Завершение подработки сохраняет её отдельную историю. Пенсия и завершение жизни закрывают обе занятости. Бизнес не совмещается с основной работой или подработкой; карьерная кнопка увольнения не закрывает бизнес, закрытие остаётся в предпринимательских сюжетах.

## Бизнес

`workshop`, `repair-service`, `small-shop` используют ту же `career=BUSINESS` и те же проверки/рост/кризисы, что сюжетный бизнес. Открытие однократно списывает стартовые вложения и завершает прежнюю основную работу. Вложения — отдельная операция, не повторяющийся ежемесячный расход.

`currentNetTarget` — стартовая месячная цель при полной работоспособности. Для дела из каталога:

```text
выручка месяца = (текущая цель чистого дохода career.monthlyPay + постоянные затраты) × работоспособность / 100
чистый результат = выручка − постоянные затраты
```

Сюжеты меняют `career.monthlyPay`, поэтому меняются и последующие результаты. При снижении работоспособности чистый результат может быть отрицательным. `risk` — игровой индекс, а не точная вероятность банкротства; он описывает вариант, текущая сюжетная вероятность общая. Эти параметры не получены из статистики предпринимательства.

`business.revenue/costs/net` — фактические операции **текущего** дела за 12 месяцев; стартовые вложения отдельно входят в общие расходы. Для старого/сюжетного бизнеса без нового профиля затрат известен только чистый доход, выручка и затраты `null`, `grossBreakdownKnown=false`. Если старые начисления вообще не связаны с ID бизнеса, чистый итог также `null`, а сами деньги остаются в общей сводке. Новая детализация не подменяет прежние платежи.

## Накопления

Реализованы `cash` (без начислений) и `deposit` (прежние **номинальные игровые 1% годовых**, ежемесячно на положительный денежный остаток до движений месяца). Выбор сохраняется, сам по себе денег не перемещает. Доход вклада в этой упрощённой модели не отрицательный; инфляция, комиссии и банковское банкротство не моделируются. Старые сохранения без стратегии продолжают прежнее начисление вклада. Новое управление стратегией доступно с 18 лет; прежние детские начисления не менялись.

`bonds`, `balanced-fund`, `equity-fund`, `world-index`, `trading` возвращаются с `available=false`, объяснением и `annualBasisPoints=null`. Их будущая доходность не выдумывается и выбор запрещён. Существующие сюжетные инвестиционные активы с возможным убытком продолжают работать отдельно от стратегии денежного остатка.

## Обязательства, прогноз и продажа

Для обязательства: `principal` — остаток основного долга, `annualBasisPoints` — годовая ставка, `nextMonthlyInterest` — ближайшие проценты, `plannedPrincipalPayment` — плановый основной платёж. Срок `scheduledMonthsRemaining=null`, поскольку реальное погашение зависит от наличия денег. У старых залогов код предмета связывается с исходной подходящей покупкой; новые залоги записывают устойчивый ID актива. Неизвестная связь возвращается `assetId=null`.

Прогноз на два месяца вычисляется на копии состояния тем же `AdultEconomy`. Учитываются текущие выплаты, работоспособность, затраты дела, содержание, жизненные расходы, дети, лечение, проценты, пенсия и основной долг. Не учитываются будущие случайные события, смерть и ещё не принятые решения. `requiredPayments` включает плановый основной платёж даже при нехватке наличных. `projectedBalance = balance + expectedIncome − requiredPayments`; `deficit=max(0,-projectedBalance)`. Это условный прогноз, а не обещание неизменного дохода. При COMPLETE будущих начислений нет.

Правила цены продажи явно игровые:

- Инвестиционный актив: текущая оценка × доля собственности.
- Имущество: 75% учётной оценки × max(20%, 100% − 5% за полный год владения) × доля собственности.

Предпросмотр возвращает `salePrice`, `debtPayoff`, `net=salePrice−debtPayoff`, `balanceAfterSale`, ID закрываемых обязательств, прекращаемое годовое содержание и новый прогноз. Если залоговый долг превышает цену, допускается доплата из имеющихся средств; при нехватке продажа недоступна. Чистое поступление может быть отрицательным.

Атомарная продажа проводит выручку и погашение связанного долга, удаляет актив, сохраняет историю приобретения со статусом **SOLD** и отдельную историю продажи. После этого содержание не начисляется, объект можно заново купить под новым ID, повторная продажа старого ID запрещена. Продажа собственного жилья переводит жилищное состояние в RENTED_HOME с обычными расходами на жизнь. Частичная продажа доли не поддерживается: продаётся вся принадлежащая персонажу доля.

**Арендные доходы пока отсутствуют в движке.** Поэтому `rentalModelled=false`, `rentalIncomeStopped=null`; сдаваемые квартиры не изображаются работающей механикой. Аналогично в источниках доходов показываются только реальные проведённые поступления, фиктивной аренды нет.

## Команды и ошибки

Пример команды (в браузере отправлять с `credentials: 'include'` и уникальным UUID в `Idempotency-Key`):

```http
POST /api/v1/sessions/{sessionId}/budget/actions
Content-Type: application/json
Idempotency-Key: 7bc76b7c-920a-42a8-9973-657963357b59

{"expectedVersion":12,"action":"TAKE_SIDE_JOB","optionId":"weekend-help"}
```

| action | optionId |
| --- | --- |
| APPLY_JOB | ID основной вакансии |
| REQUEST_RAISE | results / tenure / responsibility |
| QUIT_JOB | ID текущей основной занятости из income.primary или jobs.current |
| TAKE_SIDE_JOB | ID предложения подработки |
| QUIT_SIDE_JOB | ID текущей дополнительной занятости |
| OPEN_BUSINESS | ID варианта бизнеса |
| SET_STRATEGY | ID стратегии |
| SELL_ASSET | ID актива из каталога и предпросмотра |

Сервер не принимает цену, зарплату, доходность, долг или последствия от клиента. Перед продажей использовать `version` предпросмотра как `expectedVersion`. Пример поля ответа внутри **полной Session**:

```json
{
  "budgetAction": {
    "status": "APPLIED",
    "code": "OK",
    "message": "Трудоустройство подтверждено; начисления начнутся за следующие месяцы",
    "month": 360,
    "currency": "RUB",
    "periodMonths": 1,
    "amounts": {"basePay": 5000.00}
  }
}
```

Суммы примеров условные: использовать фактические значения сервера. При отказе найма/повышения HTTP 200, `budgetAction.status=DECLINED`, `code=APPLICATION_DECLINED`, `amounts={}`, Session/version/savedAt остаются прежними. Исход хранится в таблице команд. Обычный GET Session и прежние команды возвращают `budgetAction=null`; это результат запроса, а не новая копия игрового состояния.

Повтор одинакового ключа и тела возвращает **сохранённый исход** и **актуальную Session**, которая могла измениться после других действий. Повторное списание/продажа/случайный исход исключены. Иной запрос с тем же ключом — `409 IDEMPOTENCY_CONFLICT`. Сессионная блокировка сериализует конкурирующие изменения; из двух разных команд с одной версией применяется одна, вторая получает `VERSION_CONFLICT`.

| HTTP / code | Причина |
| --- | --- |
| 400 INVALID_REQUEST / INVALID_BUDGET_ACTION | Невалидное тело, неизвестная команда или вариант |
| 401 | Нет действующей cookie |
| 404 SESSION_NOT_FOUND | Сессия отсутствует или чужая |
| 409 VERSION_CONFLICT | Нужна актуальная версия |
| 409 IDEMPOTENCY_CONFLICT | Ключ уже использован для другого тела |
| 409 BUDGET_UNSUPPORTED / ADULT_AGE_REQUIRED | Неподдерживаемый провайдер/режим или возраст до 18 |
| 409 SESSION_COMPLETE / BUDGET_ACTION_BLOCKED | Жизнь завершена, здоровье 0 либо ожидает решения |
| 409 BUDGET_ACTION_UNAVAILABLE | Ограничения вакансии, повышения, бизнеса или нехватка средств для открытия/погашения залога |
| 409 STRATEGY_UNAVAILABLE | Стратегия пока не реализована |
| 409 JOB_CHANGED / ASSET_UNAVAILABLE | Прежняя работа/подработка/актив более не актуальны |

При pendingDecision все новые финансовые изменения заблокированы, включая увольнение и стратегию; GET остаются доступны. Это исключает изменение условий уже предложенного решения. При ошибках валидации/доступности транзакция откатывается, ни жизнь, ни деньги, ни история не меняются. Для отказа вероятностного действия сохраняется только исход команды. Не повторять отказ автоматически; при сетевой неопределённости повторять исходное тело с тем же ключом.

## Подключение frontend без изменения вёрстки

1. Обновить типы/декодеры по OpenAPI 0.11.0: новые обёртки, nullable поля, `Session.budgetAction`, поля операций и `PurchasedItem.status=SOLD`. Не считать `null` нулём.
2. При открытии существующих окон читать соответствующий GET для **текущего ID**. Не создавать новую жизнь. Не пересчитывать доходы, цену, проценты или выплаты на клиенте.
3. Показывать `total/monthlyAverage`, серверные категории, работу/подработку, фактический результат бизнеса, обязательства и условный прогноз. Для фильтров вакансий использовать `noExperience/experienceMatch`, для блокировки — `available/reason`.
4. Отправлять только `expectedVersion/action/optionId`, cookie и один Idempotency-Key на намерение пользователя. На время POST блокировать повторное нажатие. Не отправлять команду на каждом кадре или тике анимации.
5. После HTTP 200 заменить Session полным ответом; отдельно обработать APPLIED/DECLINED. Затем перечитать `/finances` и открытые разделы. DECLINED не означает устройство на работу.
6. Перед продажей загрузить предпросмотр, показать сумму долга/чистое поступление/содержание/прогноз. После подтверждения отправить SELL_ASSET с версией предпросмотра. При конфликте перечитать данные и заново предложить подтверждение.
7. Для неподдерживаемых/недоступных действий показать причину. Не имитировать аренду, доходность фондов или недостающую детализацию старой жизни. Сохранить существующие маршруты покупок и работу 1in8b.

## Проверки

Новые `BudgetManagementTest` и `BudgetManagementIntegrationTest` проверяют сверку итогов и категорий, отделение FINANCING, найм/отказ/повышение, прекращение зарплаты, совмещение и нагрузку, бизнес и единственное стартовое списание, стратегии, продажи с залогом и без, прекращение содержания, недостающие средства, сохранение JSON, старые поля, cookie/владельца, версии, повтор и конкуренцию, pendingDecision и COMPLETE. HTTP-чтение и предпросмотр сравниваются с полной строкой сохранения до запроса. Исход отказа проверяется в PostgreSQL и при повторном запросе.

Результаты полной регрессии и Docker-проверки фиксируются в `docs/budget-verification-2026-11-27.md` после завершения.
