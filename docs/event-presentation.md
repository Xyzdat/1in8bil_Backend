# Важность событий и последствия выбора — API 0.9.1

26.11.2026. Изменения добавляют необязательные nullable-поля к прежним ответам Session. Маршруты, запросы, авторизация, `expectedVersion` и `Idempotency-Key` прежние. Frontend не изменён.

## Важность события

Каждый элемент `state.history` собственной симуляции получает:

```json
{
  "id": "local-38-drawing_choice-answer",
  "importance": 21,
  "importanceSource": "LIFE_STORY"
}
```

Число в примере условное; использовать серверное значение, не вычислять его по тексту.

- `importance`: 0–100, игровая оценка значимости, не моральная оценка и не вероятность.
- `importanceSource=LIFE_STORY`: текущий сохранённый балл связанной истории из `life_highlights.candidates`. Используются **все** кандидаты, а не только выбранные слайды. Все явно связанные события этой истории, включая вопрос, получают её текущую оценку. При долгосрочных последствиях балл ранних событий может измениться. Финальность подбора задаётся `highlights.status=FINAL`.
- `importanceSource=EVENT_RULE`: базовые правила `event-importance-1`. Рождение — 50, смерть персонажа — 100, смерть родственника — 70, вопрос до появления оценки его истории — 20, прочее — 10. Это явно игровые правила, не статистика; обычные автоматические события пока не получают отдельного анализа всех последствий. Заголовок и текст не используются для угадывания важности.
- `null` или отсутствие поля — оценка неизвестна. Внешний движок `1in8b` и прежний демонстрационный сценарий без `simulation` не получают вымышленную оценку.

Новая важность вычисляется при подготовке ответа из уже сохранённых данных. Чтение не меняет запись сессии, её версию, время сохранения или архив событий. Причинные связи старым событиям не дорисовываются. Поле не заменяет готовую подборку `highlights.slides`: по одному баллу не нужно повторно собирать слайд-шоу.

## Предпросмотр вариантов

`state.pendingDecision.options[].effects`:

```json
{
  "id": "draw",
  "label": "Попробовать рисовать",
  "effects": {
    "scope": "IMMEDIATE",
    "stats": { "relationships": 1 },
    "closeness": { "mother": 1 }
  }
}
```

Пример соответствует маме с близостью 99 и общему показателю отношений 99: прибавка ограничена 100. В другом состоянии значения будут другими.

- В `stats` передаются только ненулевые фактические разности: `health`, `happiness`, `intelligence`, `relationships`, `appearance`, `aura`. Неизвестные nullable-характеристики не считаются нулями.
- `closeness` содержит ненулевые изменения близости с существующими людьми по ключу `simulation.family[].id`. Это отдельная величина от общего показателя `relationships`.
- `scope=IMMEDIATE`: только изменения при ответе сейчас, без последующих шагов, финансовых прогнозов, навыков и скрытых продолжений сюжетов. Пустые карты не означают, что у выбора вообще нет последствий.
- `effects=null` или отсутствие — предпросмотр неизвестен. Для `1in8b` он не рассчитывается и внешних запросов ради него нет. Также `null` возвращается для выбора, который уже невозможно выполнить (например, после другой траты), и устаревшего предложения работы после пенсии. Это не обещание доступности: ошибки POST обрабатываются как прежде.
- Предпросмотр относится к текущей версии сессии. После покупки, правки характеристик или любого другого изменения нужно заменить Session последним ответом backend. Фактический выбор требует прежнего `expectedVersion`; конкурентное изменение даст 409.

Предпросмотр запускает ту же непосредственную обработку ответа на отдельной рабочей копии. Она не записывается, не двигает время и не меняет исходный генератор случайных чисел. Взрослые ответы используют воспроизводимый seed сохранённого состояния. Последующие стадии сюжетов не выполняются. На GET не вызываются `SessionService.apply`, сохранение JPA, трекер ключевых решений или внешний провайдер.

Исторические `offeredOptions` внутри `EventLink`/подборки не получают задним числом новые предпросмотры. Для уже принятого решения есть сохранённые фактические `statChanges` и `closenessChanges` в `highlights`.

## Имя и фамилия

`character.name`, `simulation.family[].name` и имя в списке сохранений передаются целиком, без разбиения по пробелам. Если пользователь или 1in8b уже передал имя с фамилией, фамилия сохранена в той же строке. Отдельные `firstName`/`lastName` не добавлены: по одной строке невозможно надёжно разделить имена разных стран.

После добавления `country-names-1` новые локальные жизни получают полные имена из отдельного справочника для 36 стран. Старые жизни сохраняют прежние имена и способ генерации NPC. Формат API тот же; правила и ограничения — [country-names.md](country-names.md).

## Что передать чату frontend

Обновить типы и декодеры по `docs/openapi.yaml` 0.9.1. Принимать необязательные nullable `history[].importance`, `importanceSource`, `pendingDecision.options[].effects`. В существующем отображении событий использовать серверную важность, у вариантов — ненулевые изменения из `stats` и `closeness` (имена родственников сопоставлять по ID). Не прибавлять предпросмотр к характеристикам: после ответа брать новый Session. Не обещать отсутствие будущих последствий при пустом объекте, скрывать неизвестный предпросмотр. Имена выводить целиком из `name`. Заменять всю историю из нового ответа, чтобы обновлялась важность прежних событий. Вёрстку, стили и расположение блоков не менять.

## Изменённые файлы

- `engine/LifeState.java`: необязательные поля событий и вариантов; прежние конструкторы сохранены.
- `engine/StatChanges.java`, `highlights/HighlightTracker.java`: общий расчёт разностей характеристик для предпросмотра и уже принятых решений.
- `highlights/HistoryImportance.java`: отображение текущих оценок всех связанных историй и базовых событий.
- `session/SessionPresentation.java`, `SessionService.java`, `LifeSession.java`: подготовка ответа без изменения сохранения, подключение ко всем ответам Session.
- `SessionPresentationTest.java`, `HistoryImportanceTest.java`, `EventPresentationIntegrationTest.java`, `GeneratedLifeTests.java`: проверки предпросмотра, истории, старого JSON, полного имени и подменённого внешнего провайдера.
- `docs/openapi.yaml`, `docs/integration.md`, этот документ: контракт и требования интеграции.

Новые таблицы и миграции не нужны: обязательная структура сохранения не меняется, вычисленные оценки и предпросмотры не записываются в исходное состояние. При обычном сохранении действия новые nullable-поля могут сериализоваться как `null`; чтение прежних записей ничего не переписывает.

## Результаты проверки 26.11.2026

- Выборочные проверки: 8 тестов моделей/контракта и 11 HTTP-тестов прошли.
- Полный `mvnw test`, включая добавленную проверку ауры: **97 тестов, 0 ошибок, 0 пропусков**; выполнен аудит 1 000 полных жизней.
- Проверены совпадение предпросмотра с реальным ответом, ограничение шкал, близость по ID, аура, смертельный выбор, недоступный по средствам выбор, неизменность состояния/бюджета/сюжетов при просмотре, старый JSON, авторизация и повторная отправка.
- HTTP GET старого сохранения дважды вернул одинаковый ответ; полная запись БД до и после GET совпала. Имя с несколькими словами сохранено целиком; внешний провайдер подменён, чтение не вызывало его API.
- Docker-образ собран и запущен на `http://localhost:8081`. Backend и PostgreSQL имеют статус `healthy`, `/api/v1/health` отвечает `UP`.
- Непосредственно до и после перезапуска: **137 сохранений**, одинаковая контрольная сумма записей `9131f30ae2d24eef921a6ba1ac5def4f`. База не мигрировалась и существующие жизни обновлением не переписывались.

Для ручной проверки откройте ответ существующей локальной сессии в Network: проверьте `state.history[].importance`. Дойдите до вопроса и посмотрите `pendingDecision.options[].effects`; после ответа сравните указанные разности с новыми `state.stats` и `simulation.family[].closeness`. Отдельная генерация новой жизни для этих полей не требуется.
